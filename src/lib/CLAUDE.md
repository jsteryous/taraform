# DB & API conventions

> All data access is direct-to-Supabase (anon key + RLS) since the 2026-06-10 Railway decommission.

**The data layer is two files, both here.** `contacts.js` owns every `property_crm_contacts` / `contact_offers` read (list page, full contact, drift re-check, bulk export) plus contact insert/upsert/delete; `api.js` owns clients, members and offer mutations, with clients/members going through the RPCs in `db/20260610_clients_rls.sql`. Neither imports React. `errors.js` turns a thrown PostgREST/network error into a user-facing sentence.

Components and `AppContext` call these — they don't build `supabase.from(...)` queries themselves. The reason is the filter boundary: `buildQuery` in `contacts.js` is the single place a filtered contact query is shaped, which is what keeps the list, the row count, pagination, the drift re-check and the CSV export from disagreeing. (Two callsites still predate this rule and query Supabase directly — `StatsBar.jsx` and `ImportModal.jsx`. Move them when you next touch them.)

**`property_crm_contacts.id` and `contact_offers.id` are DB-owned bigint sequences** (`db/20260613_id_defaults.sql`). Insert new rows **without** an `id` and read the generated one back via `.select()` — `saveContact` does this for contacts, `addOffer` for offers. Do NOT client-mint ids (the old `Date.now()` path collided across members/devices). Never pass a string (e.g. UUID) — bigint column will reject it.

**Array-ish columns on `property_crm_contacts` are `jsonb`, not `text[]`.** `phones`, `tax_map_ids`, `property_addresses`, `activity_log`, `custom_fields` — all jsonb. PostgREST containment uses JSON array syntax `cs.["value"]`; the text-array form `cs.{value}` returns `22P02 invalid input syntax for type json`. Likely backed by GIN indexes for fast containment lookups.

**`custom_field_definitions` is a TEXT column** (not JSONB). Always parse with `parseCustomFieldDefs(raw)` from `utils.js` — never bare `JSON.parse`.

**Dormant tables** (`sms_settings`, `sms_messages`, `sms_templates`, `email_messages`, `email_templates`, `email_tokens`, `*_followup_queue`) hold historical SMS/email data from the retired Railway server. No UI reads them; don't delete without asking. If `sms_settings` is ever touched again: no uniqueness constraint on `(key, client_id)` — never `.upsert()` without `onConflict`, and use `.maybeSingle()`.

**`follow_up_on` is a `date` (not timestamptz)** — the user picks a day; "due" means local-today or earlier, compared as `YYYY-MM-DD` strings client-side (`isFollowUpDue`/`todayStr` in `contactFilters.js`). Persist `null` when unset, never `''`. The "due for follow-up" predicate is derived at read time (manual date arrived, OR eligible status + `last_note_at` older than that status's window) — there is no queue table or job to sync. Windows are per-status: `followUp.days` is the default, `followUp.statusDays` overrides it per status (Hot Lead = 7d), resolved by `followUpWindow`. The server clause emits one `and(...)` branch per *distinct* window, so adding a status with a new cadence widens the `or(...)`, it doesn't just extend an `in.()` list.

**A note is a call, and logging one schedules the next.** `followUpCadence.js` owns that: `scheduleAfterNote` counts the notes in the log and writes `follow_up_on` = today + the gap for that attempt (`attemptDays: [0,3,7,14,30,60]` then `repeatEvery: 60` — so +3, +4, +7, +16, +30, +60…). `ContactDetail.handleNotesChange` is the only caller and sends it in the same `updateMultiple` as the log. Three-valued return on purpose: a date, `null` to clear, `undefined` to leave the field untouched. **Gaps are applied from the day of the call, not from a day-0 anchor** — falling a week behind must not compress the rest of the schedule. A *future* date is a commitment and outranks the cadence; a due-or-past one gets rescheduled. Off-cadence statuses keep the old rule (logging a note clears a due date).

**`followUp.excludeStatuses` beats everything, including a manual date.** The queue's manual-date branch used to be status-blind, which was harmless while dates were rare and hand-set. The cadence puts one on every contact it calls, so without the exclusion a lead called once and then marked Dead/Pass would resurface every 60 days forever. It's enforced in `applyContactFilters` (and mirrored in `isFollowUpDue` for the badge), which covers every writer at once rather than just the one UI path.

**Entering an excluded status also clears the date** (`clearOnStatusChange`, wired to the status `<Select>` in ContactDetail; `scheduleAfterNote` does the same when a note is logged on one, ahead of the future-date rule). Filtering alone was not enough in practice: the contact still showed a live-looking follow-up date with no way to tell a retired one from a real appointment. So the rule is belt *and* braces — the filter is the invariant, the clear is what makes the contact honest about itself. `Offer Rejected/NFS` belongs in this list and was missed at first, which was a real hole: unlike Dead/Pass and Closed it wasn't excluded, so an NFS lead with a scheduled date surfaced as a call. **`Offer Made` is deliberately not excluded** — an offer out is an active deal and its date is a genuine appointment.

**`contact_offers.client_id` is now reliable and `NOT NULL`** (as of `db/20260806_close_cross_tenant_insert.sql` — the constraint was added successfully, which proves no null rows remained; this entry previously said "unreliable, null on older rows"). Filtering by `client_id` directly is safe. Joining through `property_crm_contacts` is still correct and is what the RLS policy itself does — the policy gates on `contact_id`, not `client_id`, so a row's visibility follows its contact.

**Tax map IDs are unique within a county, not globally.** Same parcel ID can exist in different counties — duplicate detection (`AddContactModal.findDuplicates`, `ImportModal.findDuplicate`/`buildLookupMaps`) must key by `county|taxMapId`, not `taxMapId` alone.

**Supabase auth token storage:** `localStorage['sb-ykuenmwfxecmmqichwit-auth-token']`. The LandID Chrome extension reads this to share auth — coordinate before changing storage strategy (storageKey, custom storage, cookie-based) or bumping supabase-js across token-format changes.
