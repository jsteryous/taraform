# DB & API conventions

> All data access is direct-to-Supabase (anon key + RLS) since the 2026-06-10 Railway decommission.

**The data layer is two files, both here.** `contacts.js` owns every `property_crm_contacts` / `contact_offers` read (list page, full contact, drift re-check, bulk export) plus contact insert/upsert/delete; `api.js` owns clients, members and offer mutations, with clients/members going through the RPCs in `db/20260610_clients_rls.sql`. Neither imports React. `errors.js` turns a thrown PostgREST/network error into a user-facing sentence.

Components and `AppContext` call these — they don't build `supabase.from(...)` queries themselves. The reason is the filter boundary: `buildQuery` in `contacts.js` is the single place a filtered contact query is shaped, which is what keeps the list, the row count, pagination, the drift re-check and the CSV export from disagreeing. (One callsite still predates this rule and queries Supabase directly — `ImportModal.jsx`. Move it when you next touch it. `StatsBar` moved 2026-11-16 to `countContacts`/`countCompanies`.)

**`property_crm_contacts.id` and `contact_offers.id` are DB-owned bigint sequences** (`db/20260613_id_defaults.sql`). Insert new rows **without** an `id` and read the generated one back via `.select()` — `saveContact` does this for contacts, `addOffer` for offers. Do NOT client-mint ids (the old `Date.now()` path collided across members/devices). Never pass a string (e.g. UUID) — bigint column will reject it.

**Array-ish columns on `property_crm_contacts` are `jsonb`, not `text[]`.** `phones`, `tax_map_ids`, `property_addresses`, `custom_fields` — all jsonb. PostgREST containment uses JSON array syntax `cs.["value"]`; the text-array form `cs.{value}` returns `22P02 invalid input syntax for type json`. Likely backed by GIN indexes for fast containment lookups.

**`custom_field_definitions` is a TEXT column** (not JSONB). Always parse with `parseCustomFieldDefs(raw)` from `utils.js` — never bare `JSON.parse`.

**Notes are rows in `contact_notes`, not a field on the contact** (`db/20261113_contact_notes.sql`, `lib/notes.js`). One row per note with an author; members of a workspace read all of them, only the author can edit or delete, and an edit can only change the text. All of that is SQL — RLS, column grants (`insert (contact_id, body)`, `update (body)`) and a `contact_notes_stamp` trigger that sets author, time and `client_id` itself — so `notes.js` sends the contact and the text and nothing else. A delete or edit that RLS filters out returns **zero rows, not an error**; `updateNote`/`deleteNote` check for that.

The contact carries only the rollup: **`note_count` and `last_note_at` are maintained by the `contact_notes_rollup` trigger**, read into `noteCount`/`lastNoteAt` by `mapDbContact`, and deliberately absent from `mapContactToDb` — the app never writes them. The trigger also does **not** touch `updated_at`: that is the version `upsertContact` asserts, and bumping it from a teammate's note would make every open editor of that contact conflict. `activity_log` still exists as a frozen pre-migration copy that nothing reads or writes; drop it once a real backup exists.

**The follow-up queue is per person** (`db/20261113_last_note_by.sql`). A follow-up belongs to whoever wrote the contact's latest note — `last_note_by`, rolled up by the same trigger as `note_count`/`last_note_at` — and a contact nobody has noted falls back to `user_id`, which is the *last person to save it*, not its creator (`mapContactToDb` rewrites it on every save). Turn the facet on only through `myFollowUps(cfg.followUp, user.id)` in `contactFilters.js`; the Dashboard count, "Work the queue" and the list checkbox all do, which is what keeps them equal. It routes, it does not restrict: every member can still open and edit every contact. The Dashboard is the same for every preset and shows only the signed-in user's follow-ups and notes; the `note_activity` RPC it used to call is unused.

**A company is a contact with `kind = 'company'`, not a separate table** (`db/20261113_companies.sql`). It reuses everything a person has — phones, status, notes with authors, follow-ups, search, RLS — and keeps its whole name in `first_name` (`last_name` empty); use `displayName()` from `lib/links.js` rather than joining the two by hand. What is new is `contact_links` (company ↔ person, with the person's `title` at that company): many-to-many, because one owner has several LLCs. A trigger enforces that a link joins a company to a person **in the same workspace** — without it a member of two workspaces could leak a name across the boundary. `lib/links.js` owns the queries. Links are made three ways, all through `addConnection`: the People/Companies panel on a contact's page (which can also create the missing side — a company from a person's page, a person from a company's), the Company field on Add Contact for a person (an existing company, or a new one created on save), and the note finder. The panel reports every change through `onChanged` so ContactDetail reloads the Ways In column — colleagues are derived from these links, and before 2026-11-20 linking two people to one company didn't show them as colleagues until a refresh. **Companies are hidden from the list by default** (`filters.companies === false` in `EMPTY_FILTERS` → `kind = 'person'` in `applyContactFilters`); the Companies section under Filters picks People only / People & companies / Companies only (`false` / `true` / `'only'`), the `StatsBar` counts follow it, a search ignores `false`, and "Work the queue" turns it on so the list matches the Dashboard count. Companies are only offered in the UI when `resolveConfig().companies` is true, which today means the `banking` preset. A company's Notes tab passes its linked people as `related`, so `fetchNotes` reads one timeline across all of them; a new note always lands on the contact whose page you are on.

**`phone_sync_contacts_for()` skips `banking` workspaces.** The sync writes into each user's personal Google account, and whether bank contacts may go there is a compliance question nobody has answered. Excluded by default in SQL so the safe behaviour does not depend on someone remembering to disconnect. Remove the `not exists` clause only when that answer is yes.

**`client_users.auto_follow_up`** is each person's own on/off for the cadence in one workspace (default on), set through the `set_auto_follow_up` RPC. There is deliberately no UPDATE policy on `client_users`: the row also holds `role`. `getClients` merges it into each workspace as `autoFollowUp`; `ContactDetail.handleNotesChanged` skips scheduling when it is off.

**`follow_up_on` is a `date` (not timestamptz)** — the user picks a day; "due" means local-today or earlier, compared as `YYYY-MM-DD` strings client-side (`isFollowUpDue`/`todayStr` in `contactFilters.js`). Persist `null` when unset, never `''`. The "due for follow-up" predicate is derived at read time (manual date arrived, OR eligible status + `last_note_at` older than that status's window) — there is no queue table or job to sync. Windows are per-status: `followUp.days` is the default, `followUp.statusDays` overrides it per status (Hot Lead = 7d), resolved by `followUpWindow`. The server clause emits one `and(...)` branch per *distinct* window, so adding a status with a new cadence widens the `or(...)`, it doesn't just extend an `in.()` list.

**A note is a call, and logging one schedules the next.** `followUpCadence.js` owns that: `scheduleAfterNote` takes the contact's note count (including the note just logged) and returns `follow_up_on` = today + the gap for that attempt (`attemptDays: [0,3,7,14,30,60]` then `repeatEvery: 60` — so +3, +4, +7, +16, +30, +60…). `ContactDetail.handleNotesChanged` is the only caller: the Notes tab inserts the note, reports the new count, and the date goes out in the contact save that follows. Three-valued return on purpose: a date, `null` to clear, `undefined` to leave the field untouched. **Gaps are applied from the day of the call, not from a day-0 anchor** — falling a week behind must not compress the rest of the schedule. A *future* date is a commitment and outranks the cadence; a due-or-past one gets rescheduled. Off-cadence statuses keep the old rule (logging a note clears a due date). A status in `cadence.fixedGaps` (banking `Target: 90`) waits the same number of days after every call, whatever the attempt count; `cadenceFor(status, cadence)` resolves that, and both `scheduleAfterNote` and the ContactDetail "next +Nd" line go through it.

**A contact on a date-only status must have a date, or it never comes back.** Banking `Target` is on the cadence but not in `followUp.statuses`, so the stale-note rule can't resurface it — only `follow_up_on` can. The banking CSV import added notes without a date and stranded every imported Target that way (backfilled 2026-11-16 to last note + 90). `runBankingImport` now sets the date at insert via `importFollowUp`, which is `scheduleAfterNote` over the notes the plan gives that contact. ContactDetail spells the schedule out under the date field ("Next call …", "Comes due …" from `autoFollowUpDate`, or a warning "No call scheduled") so a stranded contact is visible instead of an empty field. Any new bulk path that adds notes must do the same.

**`followUp.excludeStatuses` beats everything, including a manual date.** The queue's manual-date branch used to be status-blind, which was harmless while dates were rare and hand-set. The cadence puts one on every contact it calls, so without the exclusion a lead called once and then marked Dead/Pass would resurface every 60 days forever. It's enforced in `applyContactFilters` (and mirrored in `isFollowUpDue` for the badge), which covers every writer at once rather than just the one UI path.

**Entering an excluded status also clears the date** (`clearOnStatusChange`, wired to the status `<Select>` in ContactDetail; `scheduleAfterNote` does the same when a note is logged on one, ahead of the future-date rule). Filtering alone was not enough in practice: the contact still showed a live-looking follow-up date with no way to tell a retired one from a real appointment. So the rule is belt *and* braces — the filter is the invariant, the clear is what makes the contact honest about itself. `Offer Rejected/NFS` belongs in this list and was missed at first, which was a real hole: unlike Dead/Pass and Closed it wasn't excluded, so an NFS lead with a scheduled date surfaced as a call. **`Offer Made` is deliberately not excluded** — an offer out is an active deal and its date is a genuine appointment.

**`contact_offers.client_id` is now reliable and `NOT NULL`** (as of `db/20260806_close_cross_tenant_insert.sql` — the constraint was added successfully, which proves no null rows remained; this entry previously said "unreliable, null on older rows"). Filtering by `client_id` directly is safe. Joining through `property_crm_contacts` is still correct and is what the RLS policy itself does — the policy gates on `contact_id`, not `client_id`, so a row's visibility follows its contact.

**Tax map IDs are unique within a county, not globally.** Same parcel ID can exist in different counties — duplicate detection (`AddContactModal.findDuplicates`, `ImportModal.findDuplicate`/`buildLookupMaps`) must key by `county|taxMapId`, not `taxMapId` alone.

**The Supabase client retries once on "JWT expired"** (`authRetry.js`, wired as `global.fetch` in `supabase.js`). supabase-js only refreshes when the *browser's* clock says the token is near expiry; after a clock jump it kept sending an expired token with no refresh attempt, and every query 401'd `PGRST303` (2026-11-20, clients failed to load). On that code alone, for `/rest/v1/` only, it forces `refreshSession()` (one shared across a burst) and replays the request. Never widen it to `/auth/v1/` — the auth client uses the same fetch and would recurse.

**Supabase auth token storage:** `localStorage['sb-ykuenmwfxecmmqichwit-auth-token']`. The LandID Chrome extension reads this to share auth — coordinate before changing storage strategy (storageKey, custom storage, cookie-based) or bumping supabase-js across token-format changes.

**Connections & Ways In** (`db/20261118_connections.sql`, design in `PLAN.md`; read and written by `lib/waysIn.js` (column, connections) and `lib/groups.js` (groups, Your groups), on when `resolveConfig().connections`, the banking preset). Tables: `contact_connections` (person ↔ person, stored `a_id < b_id`; the trigger sorts them, so send either order), `contact_familiarity` (one row per teammate per contact; "Haven't met" is no row), `contact_groups` + `contact_group_members`, `finder_ignored`. Same shape as `contact_links`: the trigger stamps `client_id`, author and time, column grants say what the app may send. Three things the grants force: write familiarity **only** through the `set_familiarity(contact_id, level)` RPC (a PostgREST upsert needs an UPDATE grant on `contact_id` that deliberately doesn't exist); `contact_groups`/`finder_ignored` are the two tables where the app sends `client_id`, checked against membership; and connections and group memberships are add/remove only except a connection's `description`/`referred_by`/`unsure`. Read the column with one call, `contact_ways_in(contact_id)` (SECURITY INVOKER, NULL for a contact you can't see). Faith groups are refused in a `banking` workspace by the database. Proof: `db/proofs/20261118_connections_proof.sql`, re-runnable on production because it always rolls back. **Colleagues** (people linked to the same company) come back from `contact_ways_in` as `colleagues`, derived from `contact_links` and never stored (`db/20261119_ways_in_colleagues.sql`). **A company's column** (`CompanyWaysInColumn`) has no ways in of its own: `fetchCompanyWaysIn` reads `contact_ways_in` for each linked person (up to 40, in parallel) and the pure `companyWaysIn` rolls them up — warmest person sets the meter and the sentence, then who's here and who knows them, connections outside the company (`via` the person), and their groups. Read-only; edits happen on the person. **The note finder** is `noteFinder.js` (pure) + `finderIndex.js` (name index over the whole workspace, not the list page) + `noteActions.js` (after a save: connect exact single full-name matches and known groups with `source_note_id`, offer the rest). It only adds, never removes.

**Dashboard outreach** (`outreach.js`, `OutreachCards.jsx`; Connections workspaces only). "Introductions to ask for" and "Reasons to reach out" are computed in the browser by the pure `planOutreach` over a neighbourhood `fetchOutreachData` reads (all familiarity, connections and group members; only the company links of known people; only the contacts those mention), so the read stays small however large an imported list gets. Same rules as `contact_ways_in`: "known" is any level (Met or Know well), a shared company is a path, nothing is inferred from note counts. **A company counts as known when anyone linked to it is known** — knowing the CFO is the relationship with the company. Until 2026-11-20 the planner only read familiarity on the company row (which nobody sets), so it offered "ask Pat, CFO there" introductions to companies whose every person was already known; that `works-at` path is gone. Pursued statuses and the "gone quiet" window default to `OUTREACH_DEFAULTS` and can be overridden by a preset's `outreach` key. The contact list also shows each person's level (yours, else the team's warmest) from `fetchFamiliarityFor`, to the right of the status in the same type; `setFamiliarity` fires a `taraform:familiarity` window event so the row updates without a refetch, and the list re-checks that row against the filters (`recheckContact`). **The "Know them" filter** reads `familiarity_level` on `property_crm_contacts` — the team's warmest level, 0 haven't met … 3 know well, kept by the `contact_familiarity_rollup` trigger (`db/20261120_familiarity_level.sql`). Like `note_count` the app never writes it and it never touches `updated_at`.

**A BEFORE UPDATE trigger must not freeze an `ON DELETE SET NULL` column.** SET NULL is carried out as an UPDATE that fires the trigger; putting the old value back breaks the foreign key, and the parent's delete fails. Until 2026-11-19 that made it impossible to delete any user who had written a note or made a company link. Let such a column go to NULL and nothing else: `if new.x is not null then new.x := old.x; end if;`.

**A company's address is the `address` column; its map pin is derived** (`db/20261120_company_address_geo.sql`, design in `PLAN.md` "Call days"). One line, typed on the company page or Add Contact, or set by the banking import. `geo_lat`/`geo_lng`/`geo_status`/`geo_matched`/`geo_at` belong to the server: the `contact_geo_guard` trigger clears them and sets `geo_status = 'pending'` whenever the address changes (from any writer), and puts back any value a client sends, so `mapContactToDb` never sends them. Only `geocode_record()` (service_role) writes them, flagged by a transaction-local `taraform.geocoding` setting. pg_cron job `geocode-pending` runs `geocode_dispatch()` every 10 minutes; it makes no HTTP call unless something is pending, and otherwise starts the `geocode-run` Edge Function, which asks the free US Census geocoder (its results may be stored; Google's may not). A failed lookup stays pending and is retried; a clean no-match is `not_found`. None of it touches `updated_at`. `mapDbContact` leaves `address` **undefined** when the row was read without it (LIST_FIELDS), so a save from a list row can't blank it. `fetchCompanyLocations` reads every company for the Dashboard map (`CompanyMap.jsx`, lazy-loaded: MapLibre GL over OpenFreeMap vector tiles, free with no key and commercial use allowed; light or dark basemap follows the body theme class. Vite bundles MapLibre, so the component calls `setWorkerUrl` with the worker file imported `?url` — drop that and the map renders blank); `lib/geo.js` sorts them into placed / pending / not found / no address. The Dashboard's **Plan a visit day** card (`VisitDayCard.jsx`, rules in `lib/visitDay.js`) reads the same rows, which is why `LOCATION_FIELDS` carries `follow_up_on`/`last_note_at`: a stop is a mapped company that `isFollowUpDue` or is Target/Prospect.

**Familiarity has three levels: Haven't met / Met / Know well** (`db/20261120_drop_know_level.sql`). "Know" was folded into Met because in practice they meant the same thing, and Met took over its weight: any familiarity makes a contact `warm` in `contact_ways_in`, anyone-has-met is enough to be the helper in an intro, and `planOutreach` treats any level as "known". `familiarity_level` keeps its numbers (1 met, 3 know well; 2 no longer occurs). In the warm sentence your own row beats a teammate's stronger one ("Call them yourself"): you need nobody else to make the call.
